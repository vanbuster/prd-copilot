# PRD Copilot — 灵感到 PRD 的质量门禁管线

> 把一句话灵感变成能过质量门禁的完整 PRD。产出必须通过三道门（红线扫描 →
> 结构自检 → 独立评审），不过门重写——**质量门是本 skill 的本体，生成只是前半截。**

## 范围判断（先做）

| 用户要什么 | 怎么办 |
|---|---|
| 从想法/灵感/文档出一份**完整产品 PRD**（0→1，11+1 模块） | **本 skill** |
| 给**某一个功能**写详细规格（微交互、状态机、异常分支） | 不属于本 skill。若装有单功能精修类 skill 则转交，否则说明后按用户意愿处理 |
| 先出产品 PRD，再对某功能展开 | 本 skill 出主文档，单功能展开同上 |

## 管线总览

```
输入（三选一或组合）          处理                                      输出
─ 一句话灵感             [1] 吸收上下文（inbox + 附件文档）
─ inbox 灵感积累    →    [2] 澄清（一轮 ≤4 问，素材越厚问越少）   →   prds/YYYY-MM-DD_主题_v1.md
─ 现成文档               [2.5] Brief（有冲突/存疑才等确认）             （质量门报告持久化在文首徽章
                         [3] 分模块生成（11+1，防截断）                  + 文末完整报告）
                         [4] 三道质量门（独立评审，P0 清零放行）
                         [5] 落盘 + 可选导出
```

## 第 1 步：吸收上下文

1. **inbox（可选的灵感收件箱）**：一个追加式纯文本文件，条目格式 `- [日期] 内容`。定位优先级：
   ①用户指明的路径 → ②当前工作目录及其常见子目录下的 `inbox.md` → ③找不到则**静默跳过**，不要说教用户"先去攒灵感"。
   对 inbox **只读**，不修改任何既有条目。
2. 找到 inbox 后，筛出与本次主题相关的条目。**用户裸说"从 inbox 出 PRD"不带主题时**：对条目做主题聚类，列出"我看到 N 个可成 PRD 的方向"供用户挑选（这次选择不占澄清额度）。
3. 用户提供的文档/链接一并读入。
4. **AI 产品判定**（决定是否追加第 12 模块）：不用关键词匹配——"智能""生成"这类词的子串匹配误报率极高（v1 已验证的坏方案）。读完描述后回答一个问题：**"这个产品的核心价值是否依赖模型推理能力？"** 判定标准见 `references/industry-templates.md`。
5. **行业模板**：根据产品语义从 6 个模板中选定，focus 领域并入生成要求。语义模糊时问用户（占澄清额度 1 问）。

## 第 2 步：澄清（硬约束）

- **硬上限 4 问，一轮打包出完**（有 AskUserQuestion 工具时一次给出全部问题；单次上限恰为 4 题，这就是上限取 4 的原因——绝不搞"4+1"的第二轮追问）。方法论见 `references/clarify-method.md`。
- **素材递减**：给了成型文档或 ≥3 条相关 inbox 条目 → 至多 2 问；素材极薄（一句话）→ 至多 4 问；信息全部清晰 → **0 问，直接跳过**。
- **每题附一句"为什么问"**，让用户看出问题的必要性，例：`（决定非功能需求的量化基准）首发平台是？`
- **素材冲突优先**：inbox 条目之间或条目与用户输入矛盾时（如一条说 C 端、一条说企业端），冲突裁决题优先占用额度，选项就是冲突的两方。
- 已经清晰的信息**不问**。用户说"你看着办"就接受，用最合理假设继续——**每个假设必须落进 PRD 第 9 模块**（假设/验证方式/备选方案），不许静默吞掉。

## 第 2.5 步：Brief（条件确认）

动笔前输出一张 ≤10 行的 Brief：一句话定位 / 选用模板及理由 / 吸收的 inbox 条目 / AI 专项是否激活及理由 / 冲突裁决结果 / 预计模块数与字数。

- **需要等用户确认才开工的情况**：吸收了 inbox 条目、检出素材冲突、或 AI 判定存疑。
- **其余情况**（如纯一句话输入）：输出 Brief 后直接开工，不阻塞等待。

## 第 3 步：分模块生成（防截断）

- **逐模块写入目标文件**（先 Write 骨架，再按模块 Edit 填充），不要一次性生成全文——单次长输出在 4000-6000 字文档上会截断，这是 v1 被验证过的坑。
- 11+1 模块的逐条输出要求见 `references/modules-spec.md`，每模块有字数目标、必含子项、表格格式。
- 编号纪律：用户故事 US1/US2…，功能点 F1/F2…，优先级 P0/P1/P2 + MoSCoW。
- 落盘路径：用户指定的目录；未指定时在当前工作目录 `prds/` 下（不存在则创建）。文件名 `YYYY-MM-DD_<主题kebab-case>_v1.md`。
- 文件头 frontmatter：

```markdown
---
title: <产品名> PRD
date: YYYY-MM-DD
version: v1
sources:
  - inbox 条目: [日期] xxx（引用了哪几条列哪几条；没有则省略此行）
  - 用户输入: <一句话概括>
template: <行业模板名>
ai_product: true/false
---
```

- frontmatter 之后、正文之前，预留一行徽章位置（过门后由第 4 步回填）：
  `> 🛡 质量门：待评审`

## 第 4 步：三道质量门（本 skill 的本体，不可跳过）

完整规约见 `references/quality-gates.md`。顺序执行：

- **门 1 · 红线扫描**（机械可判）：对全文 Grep 红线黑名单（8 条主表 + 空洞形容词扩展表）。命中 → 定位改写为量化表述 → 重扫。
- **门 2 · 结构自检**（14 项）：逐项核对（编号完整性、验收标准三路径、量化指标、异常分支、**数据引用查验**——凡引用调研/行业数据处必须有来源或"假设值，需验证"标注）。缺项 → 补齐。
- **门 3 · 独立评审**：**必须在独立上下文执行**——用 Agent/Task 工具起一个评审子代理，只喂它 ①PRD 全文 ②`references/quality-gates.md` 的评分 rubric，**不喂生成过程**。生成者不许给自己打分（自评分数通胀是已知现象，会让门禁失去公信力）。环境不支持子代理时，如实在报告标注"⚠ 自评模式，分数仅供参考"。
- **放行条件：P0 扣分项清零**（任一维度存在 P0 级扣分即不放行）。三维分数只用于展示，不作为放行依据。
- **重写最多 2 轮**，按扣分项定位到具体模块重写。2 轮后仍有 P0 项：如实输出现状交用户裁决，不死循环、不谎报通过。
- 过程输出纪律：**每道门只播报一行**（如"门 1：2 处命中，已改写重扫通过"），不铺满屏幕。

### 报告呈现（双位置）

1. **文首徽章**（回填第 3 步预留行）：
   `> 🛡 质量门通过 · 完整性 NN / 量化度 NN / 可执行性 NN · 红线 0 命中 · 自检 14/14 · 独立评审`
2. **文末 `## 附：质量门报告`**：三维分数 + 扣分项 + **「交付前需你人工确认的 N 处」清单**——汇总所有"假设值，需验证"的数据、高风险假设、2 轮内未修复的扣分项，每条给出所在模块锚点。把"AI 自动修复的"和"必须人工接管的"分开，是这份报告存在的意义。

## 第 5 步：落盘与导出

1. 告知文件路径 + 一句话摘要（总字数 / 模块数 / 门禁结果）。
2. **一次性**问一轮导出意向（如 docx / 在线文档 / 都不要），有对应导出类 skill 就转交，没有就说明。不要分多轮追问。
3. **迭代**：用户要求修改时，复制为 `_v2.md` 再改（保留 v1）。单模块精修只重写该模块，重跑门 1 + 该模块相关的门 2 项；全文级修改重跑三道门。

## 禁止事项

- 不生成"待定/TBD"——必须给建议值 + 假设条件
- 不编造数据来源——引用调研/行业数据必须标注"假设值，需验证"（门 2 第 14 项会查）
- 不跳过质量门、不自评冒充独立评审
- 不修改 inbox 既有条目
- 不在产出物里夹带自我宣传（"本 PRD 由 xx 生成"之类）

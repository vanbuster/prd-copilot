# PRD 模块清单：现代敏捷 PRD 最佳实践研究

> 研究来源：Atlassian / Kuse AI / ChatPRD / Figma
> 研究日期：2026-06-07

---

## 一、模块总览表

| 序号 | 模块名称 | 必要性 | 对技术人员的价值 | 常见遗漏点 |
|------|----------|--------|------------------|------------|
| 1 | 产品概述与元信息 | **必须** | 确定项目边界、参与人、时间节点 | 缺少文档 Owner 和状态标记 |
| 2 | 问题定义与背景 | **必须** | 理解"为什么做"，避免实现方向偏离 | 只写 what 不写 why，缺少市场/用户数据支撑 |
| 3 | 目标用户与用户画像 | **必须** | 开发/设计理解受众，做出正确的技术和 UX 决策 | 画像泛泛而谈，缺少行为模式和痛点 |
| 4 | 用户故事与使用场景 | **必须** | 直接转化为开发任务和测试用例 | 用户故事缺少验收标准，边界条件不明确 |
| 5 | 功能需求 | **必须** | 开发的核心输入，定义系统行为 | 功能和需求混为一谈，缺少优先级排序 |
| 6 | 非功能需求 | **必须** | 性能/安全/可用性的硬性约束 | 完全忽略，或写了"高性能"但没有量化指标 |
| 7 | 验收标准 | **必须** | 测试的直接依据，Definition of Done | 与功能需求脱节，缺少边界和异常场景 |
| 8 | 不做什么（Out of Scope） | **必须** | 防止范围蔓延，减少无效开发 | 不敢明确写"不做"，导致隐性范围膨胀 |
| 9 | 成功指标与 KPI | **推荐** | 提供技术优化的方向和优先级 | 指标与业务目标脱节，或指标过多无法聚焦 |
| 10 | 假设与约束 | **推荐** | 揭示技术决策的底层前提，降低返工风险 | 隐含假设未显式化，后期发现基础条件不成立 |
| 11 | 设计与交互说明 | **推荐** | 前端开发的直接参考 | 只有文字没有线框图，或设计稿与文字描述矛盾 |
| 12 | 技术规格与架构方向 | **推荐** | 指导技术选型和系统设计 | 要么完全没有，要么过度设计变成技术文档 |
| 13 | 竞品分析 | **推荐** | 提供功能优先级和技术实现的参考基准 | 只有功能对比表，缺少策略启示和差异化定位 |
| 14 | 风险评估 | **推荐** | 提前识别技术风险，规划应对方案 | 识别了风险但没有缓解措施，或过于乐观 |
| 15 | 依赖关系 | **推荐** | 排列开发顺序，识别阻塞点 | 忽略外部依赖（API、第三方服务），导致项目停滞 |
| 16 | 里程碑与发布计划 | **推荐** | 规划迭代节奏和交付节点 | 只有一个大终点，没有分阶段交付计划 |
| 17 | 开放问题 | **可选** | 标记待决策项，防止假设变成事实 | 没有跟踪机制，开放问题永远"开放" |
| 18 | 数据模型与 API 规格 | **可选** | 后端开发的精确输入 | 与实际实现脱节，或由开发自行猜测 |
| 19 | GTM 与发布准备 | **可选** | 确保技术实现支撑发布需求 | 技术/产品/市场各自为政，发布时发现功能不匹配 |
| 20 | 术语表 | **可选** | 消除跨角色沟通歧义 | 仅在领域复杂项目中需要 |

## 二、各模块详细说明

### 1. 产品概述与元信息（必须）

**内容：**
- 项目名称、版本号
- 文档 Owner、参与者（PO、设计师、开发负责人、利益相关者）
- 文档状态（草稿/评审中/已批准/已归档）
- 目标发布时间
- 最后更新日期

**对技术人员的价值：**
开发者首先需要知道"我在做什么项目"、"谁负责拍板"、"什么时候要交付"。这些元信息是团队协作的锚点。Atlassian 强调将 PRD 作为"landing page"，所有人通过它定位项目状态。

**常见遗漏点：**
- 不标注文档状态，导致团队不知道哪个版本是最新的
- 不列出参与者，开发遇到问题时不知道该找谁
- 忽略更新日期，PRD 过期后仍在使用

---

### 2. 问题定义与背景（必须）

**内容：**
- 要解决的核心问题（一句话表述）
- 问题的影响面（影响多少用户/多少收入）
- 背景数据支撑（用户调研、数据分析、市场趋势）
- 战略契合度（为什么现在做，与公司目标的关联）

**对技术人员的价值：**
Atlassian 强调"shared understanding"是敏捷 PRD 的核心。开发理解了"为什么做"，才能在实现细节上做出正确判断。如果只知道"做什么"，遇到模糊地带时无法自行决策。

**常见遗漏点：**
- 只描述"要做什么功能"，不解释"为什么用户需要这个"
- 背景没有数据支撑，靠直觉驱动
- 不说明与公司战略的关系，导致跨团队优先级冲突

---

### 3. 目标用户与用户画像（必须）

**内容：**
- 主要用户群体（2-3 个核心画像）
- 每个画像的：角色、目标、痛点、技术水平、使用场景
- 用户行为的定量数据支撑（如有）

**对技术人员的价值：**
- 开发理解用户的技术水平后，能决定 UI 复杂度和错误处理策略
- 设计师基于画像做交互设计
- 测试基于画像设计测试场景

**常见遗漏点：**
- 画像写成了"所有互联网用户"，过于宽泛没有指导意义
- 只有人口统计信息（年龄、性别），缺少行为模式和动机
- 不区分 primary user 和 secondary user

---

### 4. 用户故事与使用场景（必须）

**内容：**
- 按角色组织的用户故事列表
- 每个故事遵循："作为 [角色]，我想 [动作]，以便 [目的]"
- 关联的使用场景描述
- 故事的优先级排序（MoSCoW 或自定义）

**对技术人员的价值：**
- 用户故事是开发任务拆分的起点
- 测试用例的直接来源
- AI 编码工具（如 Cursor）可以直接从用户故事生成代码骨架

**ChatPRD 特别建议：** 将用户故事写成独立、清晰的条目，"每个故事独立陈述，让 AI 能识别具体功能需求"。避免将多个需求埋在同一段落中。

**常见遗漏点：**
- 用户故事缺少"以便 [目的]"部分，变成功能列表
- 没有优先级排序，开发不知道先做什么
- 边界用户故事（edge case）完全缺失

---

### 5. 功能需求（必须）

**内容：**
- 按模块/功能区域组织的需求列表
- 每个需求包含：编号、描述、触发条件、预期行为
- 需求之间的关联关系
- 功能优先级（P0/P1/P2 或 MoSCoW）

**对技术人员的价值：**
- 开发的核心工作清单
- 技术选型和架构设计的输入
- 工作量估算的基础

**常见遗漏点：**
- 功能描述过于笼统（如"支持搜索"），缺少具体行为描述
- 不区分"自动触发"和"手动触发"的功能
- 缺少功能的依赖关系，开发时发现前置条件不满足

---

### 6. 非功能需求（必须）

**内容：**
- 性能要求：响应时间、并发量、吞吐量
- 安全要求：认证方式、数据加密、合规标准
- 可用性要求：SLA、容错、灾备
- 兼容性要求：浏览器、设备、操作系统
- 可扩展性要求：预期增长量级
- 可访问性要求（a11y）

**对技术人员的价值：**
Figma 明确将"Non-functional requirements"列为 PRD 核心组件。非功能需求直接影响架构决策：选择什么样的数据库、是否需要缓存层、是否需要微服务架构。

**常见遗漏点：**
- 完全忽略非功能需求，只在上线后才发现性能问题
- 写了"高性能"但没有量化（应为"API 响应时间 < 200ms"）
- 不考虑无障碍要求，导致合规风险

---

### 7. 验收标准（必须）

**内容：**
- 每个功能/用户故事的验收条件列表
- 使用 Given-When-Then 或条件-行为-结果格式
- 包含正常路径和异常路径
- 包含边界条件

**对技术人员的价值：**
- 测试用例的直接来源
- "Done"的定义
- AI 编码工具（Cursor）可以直接根据验收标准验证实现

**ChatPRD 特别强调：** "为每个功能列出验收标准为要点。这些标准定义了完成定义和边缘情况。" 例如："用户可以通过邮件链接重置密码"、"链接15分钟后过期"、"无效或过期链接显示错误信息"。

**常见遗漏点：**
- 验收标准只覆盖 happy path
- 标准模糊不可测试（如"体验流畅"）
- 与功能需求重复而非补充

---

### 8. 不做什么（必须）

**内容：**
- 明确排除的功能和需求
- 排除的原因
- 未来可能考虑但本次不做的项目

**对技术人员的价值：**
Atlassian 将此作为 PRD 的核心模块之一。明确"不做什么"能防止范围蔓延，减少开发做无用功。开发者看到 Out of Scope 列表后，可以停止对某些边界场景的过度设计。

**常见遗漏点：**
- 不敢写"不做"，怕得罪利益相关者
- 没有说明排除原因，后期有人质疑时无法解释
- "不做什么"列表和"未来版本"列表混在一起

---

### 9. 成功指标与 KPI（推荐）

**内容：**
- 业务指标：收入增长、转化率、留存率
- 用户指标：活跃度、满意度（NPS）、任务完成率
- 技术指标：错误率、响应时间、可用性
- 量化的目标值和时间框架

**对技术人员的价值：**
- 为技术优化提供方向（优先优化影响核心指标的路径）
- 帮助开发理解功能的实际影响
- 为监控和告警系统的设计提供依据

**Kuse AI 观点：** "区分团队做了什么、用户经历了什么、哪些结果真正重要。这将衡量标准与产品意图对齐。"

**常见遗漏点：**
- 指标与业务目标脱节
- 只有指标没有目标值（如"提升留存率"但不说提升多少）
- 指标过多，失去聚焦

---

### 10. 假设与约束（推荐）

**内容：**
- 用户行为假设（如"用户会在移动端完成此操作"）
- 技术假设（如"现有 API 能支撑新功能"）
- 业务假设（如"付费转化率不会低于 2%"）
- 硬约束：时间、预算、技术限制、合规要求

**对技术人员的价值：**
假设是技术决策的底层前提。如果假设错误，基于此的技术实现可能需要推倒重来。显式化假设让团队在早期验证关键前提。

**Atlassian 观点：** "明确陈述假设有助于识别潜在风险和需要验证的领域。在整个项目中重新审视这些假设，可以帮助团队随着新信息出现而调整。"

**常见遗漏点：**
- 隐含假设没有被显式化（如"用户已登录"）
- 约束条件只写了时间，没有技术约束
- 假设被当作事实，没有验证计划

---

### 11. 设计与交互说明（推荐）

**内容：**
- 线框图或原型链接
- 关键用户流程图
- 交互状态说明（空状态、加载态、错误态、成功态）
- 设计规范引用（如 Material Design、公司 Design System）

**对技术人员的价值：**
- 前端开发的直接参考
- 减少开发与设计的来回沟通
- 交互状态说明防止遗漏实现

**Figma 特别视角：** Figma 建议将 PRD 与设计工具连接，使用 FigJam 作为 PRD 的协作空间，直接嵌入 Figma 设计稿和原型。

**常见遗漏点：**
- 只有效果图没有交互说明
- 缺少异常状态设计（空状态、错误态）
- 设计稿与文字描述不一致

---

### 12. 技术规格与架构方向（推荐）

**这是一个需要谨慎处理的模块。**

**应该包含的内容：**
- 技术栈建议（如"前端使用 React + TypeScript"）
- 架构方向（如"微服务架构"、"单体优先"）
- 关键技术决策及其理由
- 已知的技术约束和依赖
- 数据流和系统集成点

**不应该包含的内容：**
- 详细的数据库表结构（属于技术设计文档）
- 具体的代码实现方案
- 过于细节的 API 设计

**对技术人员的价值：**
ChatPRD 明确建议在 PRD 中包含"Technical Specifications"部分，提供"架构概述、数据模型或算法"。当技术栈和架构方向在 PRD 中明确后，AI 编码工具（如 Cursor）可以通过 `.cursorrules` 直接读取并遵守这些约束。

**关键判断标准：**
- 如果团队有独立的技术设计文档（Tech Spec），PRD 中只需写"架构方向"级别的内容
- 如果没有独立 Tech Spec，PRD 中需要包含更多技术细节
- 对于 AI 辅助开发场景，技术规格在 PRD 中的价值显著提升

**常见遗漏点：**
- PRD 完全不提技术约束，开发自由发挥导致技术债务
- PRD 变成技术设计文档，PM 写了不该写的技术细节
- 技术规格与实际技术能力不匹配

---

### 13. 竞品分析（推荐）

**在 PRD 中的位置和深度：**

竞品分析在 PRD 中的定位是"为差异化定位和功能优先级提供依据"，而不是详细的市场研究。

**应该包含的深度：**
- 3-5 个核心竞品的功能对比（聚焦相关功能，非全量对比）
- 竞品的核心优势和劣势
- 我们的差异化机会
- 对功能优先级的影响

**不应该包含的深度：**
- 完整的市场规模分析（属于 MRD）
- 竞品的商业模式分析（属于市场研究）
- 过于详细的竞品功能清单（应独立为竞品分析文档）

**对技术人员的价值：**
- 了解竞品的技术实现方式（如有信息），为选型提供参考
- 理解差异化需求的优先级

**Kuse AI 竞品分析 Prompt 模板要点：** "至少比较3个竞品在定位、核心功能、定价模型、优势、劣势和差异化机会等维度。总结对产品战略和未满足机会的启示。"

**常见遗漏点：**
- 竞品分析只有功能对比表，没有策略启示
- 只列"竞品有所以我们也要有"，缺少差异化思考
- 竞品分析与功能优先级脱节

---

### 14. 风险评估（推荐）

**内容：**
- 风险列表（技术风险、业务风险、时间风险）
- 每个风险的影响等级和发生概率
- 缓解措施和应急方案
- 风险 Owner

**对技术人员的价值：**
Figma 将"Potential risks"列为 PRD 核心组件。提前识别技术风险（如第三方 API 不稳定、性能瓶颈）可以在架构设计阶段就做防范，而不是在开发后期才发现。

**常见遗漏点：**
- 识别了风险但没有缓解措施
- 只列技术风险，忽略业务和组织风险
- 风险评估一次性完成，不随项目进展更新

---

### 15. 依赖关系（推荐）

**内容：**
- 内部依赖：其他团队的支持、共享组件
- 外部依赖：第三方 API、外部数据源、合作伙伴
- 技术依赖：基础设施、工具链、库和框架
- 依赖的状态（已确认/待确认/有风险）

**对技术人员的价值：**
依赖关系直接影响开发排期和技术选型。如果关键依赖不可用，整个功能可能需要重新设计。早期识别依赖可以规划并行开发路径。

**常见遗漏点：**
- 忽略外部依赖（尤其是第三方服务的可用性和稳定性）
- 不标注依赖的状态和风险
- 依赖关系没有在里程碑计划中体现

---

### 16. 里程碑与发布计划（推荐）

**内容：**
- 分阶段交付计划（MVP -> V1 -> V2）
- 每个阶段的核心功能范围
- 关键时间节点和依赖
- 发布标准（Release Criteria）

**对技术人员的价值：**
- 指导迭代开发节奏
- 帮助开发理解当前阶段的功能边界
- 为持续集成和发布流程提供依据

**Figma 强调：** "在全面开发开始之前创建发布标准，这样团队就能确切知道产品发布前需要完成什么。" 包括：时间线和预算、性能指标、项目范围、持续维护需求。

**常见遗漏点：**
- 只有一个大终点，没有分阶段计划
- 里程碑之间没有明确的交付物
- 发布标准模糊（如"基本可用"而不是具体的可测试条件）

---

### 17. 开放问题（可选）

**内容：**
- 待决策的问题列表
- 每个问题的 Owner 和截止日期
- 问题的状态（开放/已决定/已推迟）

**对技术人员的价值：**
Atlassian 建议"创建一个'我们需要决定或研究的事项'表格来跟踪这些项目"。明确标记开放问题，防止开发者将未决定的假设当作事实来实现。

**常见遗漏点：**
- 开放问题没有跟踪机制，最终被遗忘
- 没有 Owner，无人推动解决
- 没有 SLA，问题一直悬而未决

---

### 18. 数据模型与 API 规格（可选）

**内容：**
- 核心数据实体和关系
- 关键 API 端点（如已有）
- 数据格式和字段约定

**对技术人员的价值：**
对于 AI 辅助开发，ChatPRD 的示例 PRD 中明确包含了数据模型信息："利用后端 API 中现有的 Task 模型（字段：id, title, dueDate, completed, categoryId, createdAt）"和"API 端点已存在...使用 POST /tasks 和 PUT /tasks/{id} 端点"。这使 AI 能生成与现有系统一致的代码。

**常见遗漏点：**
- PRD 中的数据描述与实际实现不一致
- API 端点描述过于模糊
- 不标注哪些是已有的、哪些是需要新建的

---

### 19. GTM 与发布准备（可选）

**内容：**
- 产品定位与核心信息
- 发布渠道和节奏
- 市场/销售/客服的 enablement 需求
- 发布后的监控计划

**对技术人员的价值：**
确保技术实现支撑发布需求（如需要的数据埋点、A/B 测试基础设施、客服后台工具等）。

**常见遗漏点：**
- 技术/产品/市场各自为政
- 发布后监控计划缺失
- 不考虑客服/运营团队的工具需求

---

### 20. 术语表（可选）

**内容：**
- 领域特定术语的定义
- 缩写全称
- 易混淆概念的辨析

**对技术人员的价值：**
消除跨角色沟通歧义，尤其在新成员加入或跨团队协作时。

**常见遗漏点：**
- 只在领域复杂项目中需要，简单项目不必添加
- 术语定义与行业标准不一致

## 三、AI 编码友好的 PRD 结构建议

基于 ChatPRD 和 Kuse AI 的研究，当 PRD 用于 AI 辅助开发（如 Cursor、Claude Code）时，以下结构化建议特别重要：

### 3.1 结构化格式

```
PRD 应使用 Markdown 格式，包含：
- 清晰的标题层级（H1 -> H2 -> H3）
- 列表项而非长段落
- 编号引用（US1, US2...）便于交叉引用
- 代码块标注数据模型和 API 示例
```

### 3.2 AI 可解析的关键模块

| 模块 | AI 编码价值 | 格式建议 |
|------|-------------|----------|
| 用户故事 | 直接生成组件和函数骨架 | 编号列表，As-a/I-want/So-that 格式 |
| 验收标准 | 自动生成测试用例 | 每个标准独立要点 |
| 约束条件 | 约束代码生成范围 | 独立章节，要点列表 |
| 技术规格 | 指导技术选型 | 明确技术栈和架构 |
| 数据模型 | 生成类型定义和接口 | 代码块格式 |
| API 规格 | 生成 API 调用代码 | 端点 + 方法 + 参数 |

### 3.3 PRD + .cursorrules 的协作模式

ChatPRD 提出了"PRD + Rules = Powerful Trio"的理念：
- **PRD 定义"做什么"**：功能、行为、约束、验收标准
- **Rules 定义"怎么做"**：编码规范、技术栈、架构模式
- **AI 执行"实现"**：根据 PRD 和 Rules 生成代码

这意味着 PRD 中应该包含足够的"技术约束"让 AI 知道边界，但不需要包含"实现细节"。

## 四、竞品分析在 PRD 中的定位

### 应该在 PRD 中出现的深度

| 维度 | 包含 | 不包含 |
|------|------|--------|
| 功能对比 | 核心功能的竞品差异 | 全量功能对比表 |
| 定位 | 差异化定位策略 | 完整市场定位分析 |
| 技术参考 | 竞品的技术方案亮点（如有） | 竞品技术架构详情 |
| 策略启示 | 对功能优先级的影响 | 独立的竞品研究报告 |

### 推荐格式

```
## 竞品分析

### 核心竞品
| 竞品 | 核心功能 | 优势 | 劣势 | 我们的差异化 |
|------|----------|------|------|-------------|
| ... | ... | ... | ... | ... |

### 对功能优先级的影响
- 功能 X 优先级提升，因为竞品 A 的同类功能用户反馈差
- 功能 Y 可以推迟，因为目前无竞品覆盖，有时间窗口
```

## 五、技术实现建议在 PRD 中的边界

### PRD 中应该出现的技术内容

| 类型 | 示例 | 理由 |
|------|------|------|
| 技术栈约束 | "前端使用 React + TypeScript" | 影响功能实现方式 |
| 架构方向 | "采用微服务架构" | 影响功能拆分和团队分工 |
| 集成约束 | "必须对接现有 Auth 系统" | 影响功能设计 |
| 性能要求 | "API 响应 < 200ms" | 影响技术选型 |
| 安全要求 | "数据传输必须加密" | 影响实现方式 |
| 已有技术资产 | "复用现有 Task 模型" | 避免重复开发 |

### PRD 中不应该出现的技术内容

| 类型 | 示例 | 应该放在 |
|------|------|----------|
| 数据库表结构 | "创建 tasks 表，字段为..." | 技术设计文档 |
| 代码实现方案 | "使用 Redux middleware 处理..." | 代码实现 |
| 部署架构 | "使用 K8s 部署，配置..." | 运维文档 |
| 第三方库选型细节 | "使用 axios 替代 fetch" | .cursorrules / 技术规范 |

### 判断原则

**"这个信息是否影响产品行为或功能的定义？"**
- 是 -> 应该在 PRD 中
- 否 -> 应该在技术文档中

## 六、风险评估/依赖关系/里程碑：是否应该加入

### 结论：这三个模块在中等以上复杂度项目中推荐加入

| 模块 | 简单项目 | 中等复杂度 | 大型/跨团队项目 |
|------|----------|-----------|----------------|
| 风险评估 | 可选 | 推荐 | 必须 |
| 依赖关系 | 可选 | 推荐 | 必须 |
| 里程碑 | 推荐 | 推荐 | 必须 |

### 判断标准

1. **风险评估**：如果项目涉及新技术、外部依赖、或有硬性合规要求 -> 必须加入
2. **依赖关系**：如果功能涉及多个团队协作或外部系统 -> 必须加入
3. **里程碑**：如果交付周期超过 2 周 -> 推荐加入

## 七、不同场景的 PRD 模板配置

### 场景 A：快速迭代功能（1-2 周小功能）

```
必须模块（精简版）：
1. 产品概述（简要）
2. 问题定义（1-2 句）
3. 用户故事（2-5 个）
4. 功能需求（要点列表）
5. 验收标准（要点列表）
6. 不做什么（要点列表）
```

### 场景 B：中型功能/版本（1-3 月）

```
必须模块：
1-8（全部必须模块）

推荐模块：
9. 成功指标
10. 假设与约束
11. 设计与交互说明
12. 技术规格（简要）
13. 竞品分析（简要）
14. 风险评估
15. 依赖关系
16. 里程碑
```

### 场景 C：大型项目/新产品（3 月以上）

```
全部 20 个模块，根据项目特点调整深度。

特别注意：
- 模块 12（技术规格）需要更多细节
- 模块 13（竞品分析）需要独立研究支撑
- 模块 14-16（风险/依赖/里程碑）必须有
- 模块 18（数据模型）推荐加入
- 模块 19（GTM）如果涉及新市场则必须加入
```

### 场景 D：AI 辅助开发（Cursor / Claude Code）

```
在任意场景基础上，额外注意：
- 所有模块使用 Markdown 格式
- 用户故事编号引用（US1, US2...）
- 验收标准写成独立可测试的要点
- 技术约束写成独立章节
- 已有数据模型和 API 用代码块格式
- PRD 放在项目 docs/ 目录中
- 配合 .cursorrules 使用
```

## 八、来源参考

1. **Atlassian** - "How to create a product requirements document (PRD)"
   - 核心观点：敏捷 PRD 追求"刚好够用的上下文"，强调 shared understanding
   - 模块建议：8 个核心模块（项目信息、目标、背景、假设、用户故事、设计、问题、不做什么）

2. **Kuse AI** - "8 AI Prompt Templates for Product Managers"
   - 核心观点：AI 作为"结构化助手"而非替代作者，PRD 是持续演进的活文档
   - 模块建议：问题定义、目标用户、目标与指标、功能需求、非功能需求、假设、风险、开放问题

3. **ChatPRD** - "Best Practices for Using PRDs with Cursor"
   - 核心观点：PRD 是 AI 和人类的共同蓝图，结构化格式是 AI 可消化的关键
   - 模块建议：用户故事、验收标准、约束条件、技术规格、数据模型、API 规格

4. **Figma** - "How To Create a Product Requirements Document"
   - 核心观点：PRD 是设计协作的锚点，应连接设计工具和敏捷流程
   - 模块建议：产品概述、用途与价值、功能、用户画像与故事、用户流程、发布标准、风险、非功能需求、假设依赖约束、评估计划与指标
